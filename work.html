01 · Contract engineer, Canter Power Systems · May 2025 – present

Scheduling and messaging platform

Appointment booking and administration that stays in sync with the calendars staff already use.

  • React
  • TypeScript
  • NestJS
  • PostgreSQL
  • Prisma
  • Cronofy
  • Outlook
  • FullCalendar

Problem

Customers and staff both book appointments, but the people doing the visits manage their days in Outlook. Availability has to reflect both the published schedule and whatever is already on someone's calendar. A change made on either side has to show up on the other quickly and correctly, across time zones and for both virtual and in-home appointments.

My role

I was an early primary implementer of the new scheduling and administration modules, starting in May 2025, and I've kept maintaining and extending them since. I didn't originate the organization's earlier scheduler or all of its business rules. My part was the newer service, its admin tooling, and the calendar integration.

Approach

  • Built the base model first: locations with guarded CRUD and validation, services, schedules, and recurring hours, including different time zone requirements for virtual and in-home services.
  • Generated bookable slots from those rules, with tests around the edge cases.
  • Connected staff calendars through Cronofy: the OAuth flow, calendar connection management, and webhook channels. Calendar events create, update, and remove appointments.
  • Invalidated cached availability whenever an appointment changes, so customers aren't offered a slot that was just taken.
  • Built an admin calendar view with drag-to-reschedule, drive times, recurring schedules, time zone selection, and role-aware permissions.
  • Added guardrails, such as blocking a schedule from going live until a calendar is linked, enforced in both the API and the UI, plus live conflict checks as staff enter appointment times.
  • Recorded scheduling events in an audit trail, and added appointment confirmations, customer link delivery, and automated SMS and email touchpoints.

Constraints and decisions

  • The calendar is the source of truth for whether a person is busy. The scheduler reacts to calendar webhooks instead of asking staff to double-enter.
  • Time zones are part of the data model, not a display detail. Virtual and in-home services have different requirements.
  • Invalid states, like an active schedule with no linked calendar, are blocked in both the API and the UI so they can't reach production.

Outcome

The service went from an initial scheduling view in May 2025 to a platform with live two-way calendar sync, admin tooling, and automated customer messaging. I continue to maintain and extend it.

02 · Contract engineer, Canter Power Systems · 2025 – 2026

Cross-system estimate and survey platform

An estimate starts as a customer inquiry and goes through a site survey, equipment sizing, pricing, and a payment plan. Each step is captured by different people, at different times, in different services.

  • React
  • TypeScript
  • NestJS
  • C#/.NET
  • ASP.NET Core
  • SQL Server

Problem

Quoting a home standby generator needs a lot of structured information: what the customer wants to power, what the site looks like, which unit fits the load, current pricing, and how payment will be scheduled. Customers and sales reps both fill parts of it in, often over several sessions. The data is spread across a TypeScript integration layer and a .NET core API, and it has to stay consistent as forms change.

My role

I contributed across all three layers (the React UI, the NestJS integration API, and the .NET core API) as part of a team. In October 2026 I delivered a redesign of the estimate forms that touched four repositories. Other engineers own other parts of the platform.

Approach

  • Built multi-step customer and sales-rep estimate forms with saved drafts, so someone can stop and pick up later.
  • Kept saved drafts compatible across form versions, so drafts started before a redesign still load and submit correctly.
  • Implemented load calculations that feed generator selection.
  • Added structured site surveys with photos, including a "text me the link" handoff so someone filling out the form on a computer can take the photos on their phone.
  • Built pricebook and payment-schedule administration in the React admin console, with role-restricted pricebook editing.
  • Added revision checks on draft saves. A tab or device holding an older copy of the form gets a clear "stale draft" response instead of silently overwriting newer work.
  • Made reporting version-aware, so records from older form versions still read correctly.

Constraints and decisions

  • A form redesign is also a data migration. Old drafts and older records had to keep working, which meant versioning both the inputs and the reports built on them.
  • Changes had to ship together across four repositories (client, integration API, core API, and admin UI), so contracts between services were settled before implementation.
  • The phone handoff created a new failure mode: the customer's computer, still open on an older copy, could overwrite the photos they had just added from their phone. Every save carries the revision it was based on, and the server refuses saves based on an outdated revision.
  • Uploaded photos are scoped to the lead they belong to and validated server-side, so the public form can't be used to reach other files.

Outcome

The October 2026 redesign shipped across all four repositories with saved-draft compatibility, phone photo handoff, and version-aware reporting in place.

03 · Contract engineer, Canter Power Systems · 2026

Service operations data integration

Synchronizing customer, equipment, and maintenance data from a field-service platform into internal reporting.

  • ServiceTitan API
  • NestJS
  • TypeScript
  • PostgreSQL
  • Background jobs
  • React

Problem

Service history lived in ServiceTitan across six tenants. Internal reporting was missing customers and couldn't reliably tell which equipment was a generator, which service visits were maintenance, or which customers were covered by a maintenance plan or warranty.

My role

I built the integration from the first API connection onward: synchronization, backfills, the daily processing pipeline, query APIs, and the reporting UI. The equipment and membership-type classification rules came from a colleague's existing implementation. I ported them into the shared API and wired them into the pipeline. The rules themselves are theirs.

Approach

  • Built incremental synchronization across all six tenants, with a watermark that only moves forward so an interrupted run can't skip records.
  • Tracked down why customers were missing. The platform's list endpoint silently leaves out inactive customers unless asked for them explicitly, even though those customers still own real equipment and service history.
  • Combined the classification steps (equipment, service activity, membership types, warranty status) into one ordered daily pipeline, with a shared lock and a "last updated" freshness indicator in the admin UI.
  • Added chunked seeding so large backfills could run on a smaller staging database without dropping connections, leaving production behavior unchanged.
  • Built reporting UI, CSV exports with stable IDs for reconciliation, and a generator-unit browser for internal users.

Results

  • Inactive customers, along with the equipment and service history they own, now come through the sync instead of silently going missing.
  • Membership types across every tenant are classified as maintenance, warranty, or monitoring, and plan records were backfilled and checked in staging before production.
  • Internal users can browse generator units, filter by membership, and export CSVs with stable IDs for reconciliation.

Constraints and decisions

  • Multi-tenant source data means the same concept can be configured differently in each tenant, so classification has to account for that.
  • A third-party API's defaults are part of the contract. "List all customers" didn't actually mean all customers, and the same pattern had already appeared with another resource.
  • Large backfills run in staging first and are checked before anything touches production.

04 · Contract engineer, Canter Power Systems · 2025 – 2026

Production reliability and performance

Three problems that each had an obvious workaround and a less obvious root cause. The method was the same each time.

  1. ReproduceMake it happen on demand.
  2. MeasureGet a number, not a feeling.
  3. TraceFollow it to the root cause.
  4. FixChange the cause, not the symptom.
  5. VerifyConfirm it in production.

Database connection exhaustion

Symptom
A NestJS service intermittently failed with PostgreSQL connection-limit errors (Prisma P2037).
Root cause
Seven feature modules each listed the Prisma client as their own provider. In NestJS that creates a separate instance per module, and each instance opened its own connection pool.
Fix
Made the existing database module global and removed the duplicate providers, so the whole app shares one client.
Verified
Only the global database module provides the client now, so each instance runs a single shared connection pool.

Slow frontend builds

Symptom
Frontend builds were slow enough to hold up every deploy and review cycle.
Root cause
A safelist-generator plugin inherited from the original UI template wrote out every color and variant combination on each build, and Tailwind then had to compile all of it.
Fix
Removed the generator and let Tailwind's JIT scan the real source, then safelisted only the few classes actually built dynamically.
Verified
The build now compiles only the classes the app uses. Follow-up changes restored the few dynamically built classes the scan couldn't see.

Retries that couldn't succeed

Symptom
A calling service kept retrying appointment-create requests that could never succeed.
Root cause
A request referencing a record that didn't exist hit an unhandled foreign-key error and came back as a 500. The caller correctly treats 500s as transient, so it retried.
Fix
Mapped foreign-key violations to a 400 that names the failed reference, and left other errors unchanged.
Verified
Unit tests cover both paths. Invalid requests now fail once, with a clear error.
